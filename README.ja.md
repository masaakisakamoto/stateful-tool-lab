# Stateful Tool Lab

**予約ツールの失敗を再現し、実行後の状態で正しさを検証する小さな実験リポジトリ。**

[English](README.md) · [調査と選定理由](docs/RESEARCH.md) · [次の実験](docs/EXPERIMENTS.md) · [ツール仕様](docs/PROTOCOL.md)

2026年10月28日作成、10月29日Publicソース公開。v0.1.0、オフラインの初期実装です。

## 何を確かめるか

予約の登録自体は成功しても、応答だけがタイムアウトすることがあります。そのまま再試行すると、同じ依頼を二重登録する可能性があります。本プロジェクトは、このような場面を架空データで再現し、実行後の予約状態が正しいかを機械的に採点します。

```bash
python3 -m unittest discover -s tests -v
python3 -m stateful_tool_lab demo --output results/demo.json
```

Python 3.11以降。追加ライブラリ・APIキー・通信は不要です。

## 今回できたこと

- 12シナリオの日本語・英語対訳、計24タスク。
- 登録・キャンセル・原子的な予約変更、定員確認。
- 処理前／処理成功後の応答途絶、依頼の重複配信。
- 同じ操作キーで再試行する仕組みと、その記録の照会。
- 最終状態、余分な登録、予約ID、無関係な予約の保持、結果報告の採点。
- JSONの実行記録と、外部で作ったツール呼び出し列の再実行。

デモでは、単純な再試行は20/24、同じ操作キーを使う方式は24/24が合格しました。これは**意図的に用意した制御プログラムで評価器の動作を確認した結果**です。AIモデルの能力や、日本語での実務性能を測った数値ではありません。

## ポートフォリオとしての狙い

「どんな課題を選んだか」「何を正解と定義したか」「失敗をどう再現したか」「根拠のある比較ができるか」をコードと結果で示すことです。既存の汎用評価基盤に接続できる、小さな課題セットとして育てます。

最初の題材に予約を選んだのは、成功・失敗と副作用を具体的に定義しやすく、業務経験を課題設計に生かしやすいからです。実際の店舗や顧客のデータは使っていません。

## 次に必要なこと

実モデルを動かす前に、指示とツールだけを渡す接続口を作ります。現在のデモは構造化された依頼を直接受け取り、自然言語の理解を省略しています。その後に、モデル・実行条件・費用上限を決め、同じ条件で複数回比較します。

現在は、音声・曖昧な日時・利用者との追加確認・同時実行・権限管理・複数サービス間の補償処理に未対応です。本番予約システムや安全な実行環境として使う段階ではありません。

英語READMEに詳細な制約、デモの結果、再現手順を記載しています。GitHub上の検証結果は[Actions](https://github.com/masaakisakamoto/stateful-tool-lab/actions)で確認できます。タグ付きリリースと実モデルの性能評価は未実施です。
